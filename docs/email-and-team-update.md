# Email delivery and team management

## Deployment

1. Apply `supabase/migrations/20260915000000_email_queue_and_team_delete.sql`, `supabase/migrations/20260915010000_email_editor_and_invitation_deadline.sql`, `supabase/migrations/20260915020000_email_template_storage.sql`, `supabase/migrations/20260915030000_retry_cancelled_decision_emails.sql`, then `supabase/migrations/20260916000000_release_decision_emails.sql` before deploying this backend. If the first four are already installed, apply only the fifth. It adds waitlist support and atomic release previews without releasing decisions or sending existing applicants any emails. The registration-closure and invitation-response migrations must already exist. These create the outbox, reviewed batches, editable templates, shared invitation deadline, service-only functions, and team deletion function. They do not backfill confirmations, release decisions, send emails, or delete existing teams. The invitation deadline starts unset; the September 20 date is only a preview until an admin saves it.
2. Deploy the frontend, API and `netlify/functions/process-email-queue.ts` together. The new registration endpoint requires its database function; do not deploy it against an unmigrated database.
3. Set function environment variables: existing Supabase backend credentials, `RESEND_API_KEY`, verified `RESEND_FROM_ADDRESS`, and `EMAIL_SITE_URL` (the HTTPS origin of the registration portal). `EMAIL_DELIVERY_ENABLED=true` enables both confirmations and decision delivery. Omitted/false pauses delivery; new confirmations remain queued. Ensure the worker has the same configuration as the API.
4. Review and edit templates in Admin → Emails. Set the shared deadline in Approvals → Invitations before preparing approval emails. On staging, use a synthetic applicant and Emails → Send test email to send a test to an organizer's inbox, check the real email client rendering and dashboard link, then test a small decision batch before production use. Enabling production delivery also drains its queued confirmations.
5. Netlify runs the worker once a minute on the published production deploy. Branch/deploy previews do not run scheduled functions. Outside Netlify, schedule `npm run email:worker -w backend` once a minute (from the workspace; dotenv loads `backend/.env`). The compiled alternative is `node backend/dist/emailWorker.js` with environment variables supplied by the host.

Use `npm test`, `npm run test:database`, `npm run lint`, and `npm run build` to validate. Database tests run the actual migration in an isolated PGlite PostgreSQL instance and never connect to Supabase. They cover transactions, privileges, snapshots, retry leases and data preservation; they do not simulate multiple independent PostgreSQL connections.

## Admin workflow

- Select applicants in Approvals or Teams and open **Release decisions…**. Choose **Release without emails** or **Release and send emails**, then enable sending separately for approved, denied, and waitlisted applicants. The dialog groups selected applicants by decision and shows their email addresses. Pending or missing applications stay selected.
- Review the grouped recipients and email choices in the release dialog. Each decision is paired with its saved template. Message previews and test sending are in Emails. Confirming releases all selected decisions and queues the chosen emails in one database transaction: a queue failure rolls back the entire release. Maximum 1,000 decisions per release. Retry the same preview after an uncertain response; completed previews return their saved result.
- The Invitations view tracks released approvals and no longer duplicates the release button. Emails contains the template editor and delivery history; standalone decision-send buttons are removed. To email an already-released decision, select the applicant in All applicants and use the same release dialog. Duplicate emails for the same release are skipped.
- A reviewed preview expires after one hour. Confirmation rechecks the reviewed draft decisions, recipients, personalization, and approval deadline before releasing. Queueing then checks the resulting released decisions and timestamps; a mismatch rejects the entire action. Repeat requests for the same preview return the original result. Separate previews also deduplicate the same registration/release. A fresh reviewed preview can replace a cancelled email only when it has never been attempted; its recipient and payload are refreshed and duplicate replacement requests still queue it once. Sent or uncertain attempts cannot be replaced this way.
- **Send test email** in Emails lets an admin choose any of the four saved templates and enter one recipient address. Set the sample first name and application name and review the personalized preview before sending. These details affect only the test; the subject starts with `[TEST]`. Approval tests use the saved invitation deadline, or the September 20 sample if unset. Tests do not change applications or release decisions. They use the existing outbox and appear in History; production delivery must be enabled. Retrying an uncertain request reuses its queue key. No additional migration is required for this control.
- Admin → Emails shows confirmation, decision and test jobs, filters, retries and links to Resend logs. `Sent` means Resend accepted the request, not that the recipient opened it or that the inbox provider delivered it. Delivery/bounce investigation stays in Resend.
- **Edit email** changes the subject, message and button text. Expand **HTML template** to edit the actual HTML and inline CSS with a live preview. **Save to Storage** initializes each starter template; subsequent saves create a new revision. The private `email-templates` bucket contains `<kind>/<revision UUID>/template.html` and `settings.json`. The HTML file contains the layout and styles; the JSON file contains subject, message text and button label. These are real files, not HTML stored in a database column.
- `email_template_files` contains only the active Storage path, version and audit metadata. The backend uploads both immutable files before activating their path with a version check. Failed uploads and stale saves leave the active revision unchanged. The previous `email_templates` table is retained only for export of any legacy edits; this version never reads or writes its content and revokes the legacy save function. If that earlier version was deployed, copy any saved text into the new Storage editor before enabling delivery.
- Starter defaults are generated by `backend/src/utils/emailTemplates.ts` until a template is first saved to Storage. After activation, a missing/invalid file stops preparation instead of silently falling back. Supported HTML placeholders are `{{first_name}}`, `{{form_title}}`, `{{dashboard_url}}`, `{{logo_url}}`, `{{deadline}}`, `{{deadline_sentence}}`, `{{subject}}`, `{{button_label}}` and `{{message_html}}`. The last inserts the escaped editable message as paragraphs; other values are HTML-escaped. Approval files must retain `{{deadline_sentence}}` and `{{dashboard_url}}`. The default deadline sentence is “Please accept by …”. HTML editing is available only through authenticated admin APIs; previews use a sandboxed iframe. No React Email or Resend dashboard template is involved.
- Storage denies direct browser access, including admins signed in with ordinary authenticated tokens. The backend uses its service credentials. Keep active files immutable; edit through the admin editor so the revision checks and previews stay accurate. Failed/conflicting saves may leave inactive revision folders, which can be cleaned up after checking that no active pointer references them. Never delete files after an uncertain activation response without checking the database.
- New confirmation jobs share one template lookup and Storage download per worker pass, loaded lazily when needed. The next pass reloads the active revision so edits take effect without a redeploy. Failed lookups are also cached for that pass; affected jobs receive a retry delay (or fail after six attempts), allowing unrelated emails to continue. Decision previews load each selected template once per preview and snapshot it when prepared. Jobs with a frozen payload, including retries, do not access Storage. Reviewed and attempted payloads are frozen, so later edits do not silently alter retries or existing drafts. Resend receives both styled HTML and a plain-text alternative through its HTTP API in `backend/src/utils/email.ts`. Previously sent emails are unchanged.
- Approval links to `/dashboard`, where the existing signed-in invitation flow accepts or declines a released invitation. Visiting an email link never records an RSVP. Rejection politely invites the applicant to apply again next year. The waitlist email explains that we will email if a place opens and no action is needed now. Application first-name validation remains required when configured as required; the template's defensive fallback covers legacy or custom-form records.

## Reliability and operational limits

Creating a new registration and its confirmation job is one database transaction. Provider outages cannot lose the job or hold the registration HTTP request open. Existing applications are not automatically emailed again, and edits do not create another confirmation.

Each worker pass first expires unanswered invitations, even when email delivery is paused. It then processes at most 20 email jobs, with 600ms between jobs and a 4-second start budget that reserves up to 25 seconds (including Storage downloads) for the last job within Netlify's 30-second limit. Jobs use two-minute leases with `FOR UPDATE SKIP LOCKED`. Calls have bounded timeouts. Rate limits and temporary provider failures back off exponentially, stopping automatic retries after six attempts. Monitor queued age, failed jobs and the account's Resend quota during large waves.

The exact payload is stored before sending and Resend receives a stable `Idempotency-Key`. If Resend accepts an email but the process crashes before saving the receipt, its retry uses the same payload/key. Because [Resend retains idempotency keys for 24 hours](https://resend.com/docs/dashboard/emails/idempotency-keys), jobs stop as **Needs review** after 23 hours from their first attempt. Never clear a payload or create a fresh key for an uncertain send without first checking Resend. The UI only retries failed jobs within that safe window; sent, cancelled and needs-review jobs cannot be blindly retried. Check failures promptly; recovery beyond the window requires operator reconciliation.

Queued jobs whose registration was deleted, recipient changed, or public decision changed are cancelled at claim time. A decision changed after a worker claims a job may already be in flight; an accepted message cannot be recalled. Make corrections before queueing. Changed/re-released decisions get a new release timestamp and thus a new email identity.

No webhook is installed by this change. Admin authorization and service-only database permissions protect drafts, recipient addresses and job history. Keep Resend and Supabase secrets in backend function environments.

## Shared invitation deadline

Approvals → Invitations sets one deadline for all main-form invitations. The editor uses Eastern time. The sample **midnight Sunday (9/20)** means the end of September 20, 2026: September 21 at 12:00 a.m. Eastern (`2026-09-21T04:00:00Z`). Saving requires a warning review because the setting affects everyone. Approval emails require a future saved deadline; no sample date is silently activated in production.

After the deadline, only unanswered registrations with `released_status = 'approved'` expire. The database sets their saved and released decisions to `rejected`, their invitation response to `declined`, and `invitation_expired_at` to the cutoff. Admin lists distinguish **Expired** from an applicant's own decline. Accepted invitations and existing declines are preserved. Pending, unreleased and other-form applications are unaffected. Expiry does not automatically send a denial email.

The scheduled worker updates expired records every minute. Loading invitation settings on the applicant dashboard also runs expiry. The response function checks the database clock under locks, so an acceptance after the cutoff is rejected even if the worker has not run yet. The dashboard disables late responses and refreshes the deadline every minute. Keep the scheduled worker running for automatic database updates when nobody visits the dashboard.

Extending or removing a deadline first expires invitations whose previous cutoff already passed; it does not restore them. To invite someone again, set a future deadline, save approval and release it. Releasing a new approval clears that applicant's system-generated expiry/decline, while preserving real applicant responses on ordinary reapprovals. Accepted/declined corrections remain available through the existing admin workflow.

Changing the deadline invalidates unqueued approval previews and cancels never-attempted approval emails carrying the previous date. Attempted emails become **Needs review** so an operator can check Resend before creating a replacement. Messages already in flight or sent cannot be rewritten or recalled. A newly reviewed email with a different deadline has a new deduplication identity; saving the same deadline does not create one.

## Teams without applications

Accounts, profiles, team memberships and applications are separate records. The existing create/join endpoints require a signed-in account, but do not require a submitted application. A profile name can therefore legitimately appear on a team with no application. An existing application can also be deleted while membership remains. `Missing application` in the admin team list means no current submission for the selected form, not a missing account.

The admin list now explains that distinction and falls back to the account email when the application email is unavailable. The service-only lookup returns only requested current team members. Team membership alone does not count as an application or an approval.

**Delete team** reviews the team's current members in a warning dialog. The backend locks and rechecks the team name/membership snapshot, then deletes memberships and the team together. Accounts, profiles, applications, RSVP answers, and matching submissions remain. The old invite code stops working, and former members may create/join other teams. If the membership changed since review, refresh and review again. Deleting a team with no application is also supported.

## Separate database audit finding

The live database audit also found the legacy `registrations_user_id_unique` index, which permits only one application per account across all forms. The application now expects uniqueness per `(user_id, form_key)`. This branch leaves that existing index in place; removing it should be a separate reviewed migration after confirming the per-form unique index is present. It can block additional-form submissions, but does not explain a team member with no current application under any form.

## Delivery paused after deployment

In Netlify project configuration → Environment variables, set `RESEND_API_KEY` and `EMAIL_DELIVERY_ENABLED=true` for the production context with the Functions scope (or all scopes), then redeploy. A key scoped only to Builds is not available to the API or scheduled worker. The pause check requires both values; setting a key in a local `.env` file does not configure production. Verify `RESEND_FROM_ADDRESS` uses your verified Resend domain and `EMAIL_SITE_URL` points to the production registration portal. Enabling delivery drains existing queued emails.
